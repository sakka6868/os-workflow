# os-build：TDD 实施 + 代码审查

## 何时调用

tasks.md 就绪，用户确认后进入实施阶段。

## 开始前：并行机会评估（MANDATORY — 不得跳过）

在输出任何 GATE 声明之前，必须读取 tasks.md 并确定并行策略：

**若 tasks.md 末尾有"并行策略"章节** → 直接按 Wave 声明分配 agent。N ≥ 3 MUST 并行；N=2 SHOULD 并行（文件无重叠）；N=1 串行。

**若无"并行策略"章节** → 自行评估并输出：

```
[PARALLEL] 可并行 task 组数: <N>
[PARALLEL] 分组:
  - 组 A: <task-id 列表，无 blockedBy 或 blockedBy 已满足>
  - 组 B: <同上>
[PARALLEL] 决策: 并行（N ≥ 3）| 推荐并行（N=2，文件无重叠）| 串行（N < 2 或文件重叠）
[PARALLEL] 理由: <各组涉及不同模块/目录，无共享文件冲突>
```

**评估规则：**
1. 遍历 tasks.md 中所有 `[ ]` 状态的 task
2. 检查各 task 涉及的目录/文件是否有重叠（重叠 → 必须串行；无重叠 → 可并行）
3. **N ≥ 3 → MUST 并发；N=2 且文件无重叠 → SHOULD 并发；N < 2 → 串行**
4. 并发时各组用独立子代理（opencode: `task` / Claude Code: `Task`）并行执行
5. **前后端 task 组天然不共享文件，即使没有显式 blockedBy 也应视为不同 agent 的候选**

**子代理分配规则：**
- 每组用一个 Agent
- 各组 prompt 必须包含：具体范围、明确目标、清晰约束、预期输出格式
- 所有子代理完成后 → 逐一审查摘要 → 检查文件冲突 → 运行全量测试

**违规后果：** 未输出 `[PARALLEL]` header 不得输出任何 `[GATE]` header，不得调用 Edit/Write。

**禁止：** 跳过并行评估直接写代码；N ≥ 3 仍串行执行（除非文件重叠）；前后端独立可并行却默认串行。

## 写代码前必须声明（GATE）

在调用 Edit/Write 修改生产代码之前，必须在回复中明确输出：

```
[GATE] 当前阶段: RED | GREEN | REFACTOR | 例外(引用判定表行)
[GATE] 对应测试: <测试文件路径>
[GATE] 测试状态: ✗ FAIL（已确认红色）| ✓ 基线全绿（REFACTOR 阶段）
```

例外：依赖升级 patch、格式/注释修正、微小修复（≤5 行无逻辑变更）可声明跳过。详见 CLAUDE.md。

## RED → GREEN → REFACTOR 循环

对 tasks.md 逐项执行：

```
 ┌─────────────────────────────────────┐
 │  RED          GREEN         REFACTOR│
 │  写测试→失败 → 写最简代码→通过 → 优化结构→通过  │
 └─────────────────────────────────────┘
```

| 阶段 | 规则 |
|------|------|
| **RED** | 先写断言，再补 Arrange/Act；运行确认失败；**必须看到红色** |
| **RED（意外通过）** | 测试意外通过 → 说明被测行为已存在或测试写错 → 暂停，检查测试是否正确复现了 bug/新需求 |
| **GREEN** | 只写让测试通过的最简代码；不过度设计；不添加测试未覆盖的行为 |
| **GREEN（回归失败）** | 新代码导致已有测试失败 → 立即停止，评估是设计冲突还是副作用，用 `AskUserQuestion` 展示方案提给用户决策 |
| **REFACTOR** | 消除重复、改善命名、提取工具函数；**一次改一处，改完立即跑测试** |

### 测试原则

- ✅ 测公开 API 的输入输出："传入有效凭证返回 200 和 token"
- ❌ 不测内部函数调用次数："调用了 `hashPassword` 一次"
- 例外：对外部依赖（数据库、网络、文件系统）的调用允许 mock 并验证调用参数

每完成一项，tasks.md 中 `[ ]` 改为 `[x]`。全部测试通过后进入 Code Review。

## 并行执行

参照 tasks.md 中的 `blocks/blockedBy` 依赖声明——无依赖关系的 task 使用多个 subagent 同时处理。有 `blockedBy` 的 task 必须等待依赖项完成后才能开始。涉及同一文件的 task 串行执行。

### 并行代理调度规则

**何时并行：**
- 3 个以上不共享文件的 task 组，各自独立完成不同模块的变更
- tasks.md 并行策略中声明为不同 Wave 的 agent
- 各组不修改相同文件，无因果依赖

**禁止并行：**
- 各组修改相同文件（存在冲突风险）
- 存在 `blockedBy` 因果依赖（子代理 B 需要子代理 A 的输出才能工作）
- 需要完整系统状态理解才能正确实现

### 子代理 Prompt 结构

每个子代理的 prompt 必须包含：具体范围（哪个文件/模块）、明确目标（修什么/实现什么）、清晰约束（不改什么）、预期输出格式（摘要+变更清单）。各子代理完成后，逐一审查摘要、检查冲突、运行全量测试。

## Code Review（三阶段 + 硬性闸门）

全部 task 完成后、归档前执行。**阶段 3 未通过不得调用 `os-ship`。**

### 阶段 1 — Spec 合规审查
- 改动是否准确对应 spec 中的每个 Scenario
- 是否遗漏了 Spec 要求的边界条件
- 是否过度构建（加了 Spec 未要求的特性）
- 是否构建不足（Spec 要求的场景未全部覆盖）

### 阶段 2 — 代码质量审查（仅通过阶段 1 后）

#### 2.1 死代码与冗余
- [ ] 无未使用的 import / 变量 / 函数 / 参数
- [ ] 无被注释掉的代码块（用 git history 追溯，不靠注释保留）
- [ ] 无不可达分支（if/else 中永远不会执行的分支）
- [ ] 无冗余类型转换 / 空操作（如 `!!true`、`arr.map(x => x)`）

#### 2.2 重复代码
- [ ] 无 ≥3 行的复制粘贴代码块（提取为共享函数/组件）
- [ ] 无跨文件的相同逻辑以不同形式重写（如两个 Service 各自实现了相同的分页计算）
- [ ] 无重复的错误处理模式（提取为统一的 error handler / interceptor）
- [ ] 无重复的测试 setup/fixture（提取到 `beforeEach` 或共享 fixture 文件）
- [ ] 无重复的常量/配置值分散在多个文件中（集中到 constants / config 模块）
- [ ] 无重复的类型定义（后端 VO 和前端 type 有一致来源，不手写两份）
- [ ] 相似但不完全相同的代码块已评估是否可参数化合并（若差异仅在于一个值→加参数；若结构相似但语义不同→保留）

#### 2.3 命名与可读性
- [ ] 变量/函数/类名自解释，无单字母名（循环索引除外）
- [ ] 无歧义缩写（如 `usr`、`cnt`、`tmp` 除非有明确上下文）
- [ ] 函数名反映其副作用（`get*` 不修改状态，`set*`/`update*` 会修改）
- [ ] 无魔法数字/字符串——已提取为命名常量
- [ ] 条件表达式可直接读懂（复杂条件已提取为命名布尔函数）

#### 2.4 Code Smells
- [ ] 无过长函数（>30 行逻辑代码需拆分）
- [ ] 无过深嵌套（>3 层 if/for/try 需提取或 early-return）
- [ ] 无过长参数列表（>4 个参数需封装为对象/struct）
- [ ] 无"上帝类"（单一类承担 >3 种职责）
- [ ] 无特性依恋（方法过度访问其他对象的字段——应移到所属类）
- [ ] 无霰弹式修改（改一个功能需要同时改多个不相关文件）
- [ ] 无空 catch 块——每个异常至少 log 或 rethrow
- [ ] 无 `instanceof`/类型断言链——用多态替代
- [ ] 无循环内拼接 SQL 字符串——用参数化查询
- [ ] 无 `==` 与 `equals` 混用（Java）/ `==` 与 `===` 混用（JS）

#### 2.5 错误处理
- [ ] 所有外部调用（API/DB/文件）有 try-catch 或 error boundary
- [ ] 错误信息包含足够上下文（哪个操作 + 哪个资源 + 原始错误）
- [ ] 不在 catch 块中吞掉异常后静默返回默认值（除非有明确理由）
- [ ] 无 `throws Exception`（Java）或 `catch (e: any)`（TS）——用具体异常类型

#### 2.6 安全
- [ ] 无硬编码密钥/密码/Token（用环境变量或配置中心）
- [ ] 用户输入在输出前已做转义（防 XSS）
- [ ] SQL/命令拼接已用参数化（防注入）
- [ ] 敏感操作（删除/权限变更）有鉴权检查
- [ ] 日志中无明文密码/Token/身份证号

#### 2.7 性能
- [ ] 无循环内 DB 查询（N+1 问题）
- [ ] 无不必要的全表扫描（WHERE 条件有索引覆盖）
- [ ] 大循环内无对象分配热点（可复用的对象已提取）
- [ ] 前端无 `useEffect` 无限循环风险（依赖数组正确）
- [ ] 无不必要的重复渲染（React.memo / useMemo / shouldComponentUpdate）
- [ ] 大数据量操作有分页/分批/游标处理（不会一次加载全部到内存）
- [ ] 缓存策略已考虑（热点数据是否应该缓存？缓存失效策略是什么？）

#### 2.8 资源管理（最容易导致生产事故）
- [ ] 数据库连接/HTTP 客户端/文件流在使用后正确关闭（try-with-resources / finally / useCallback cleanup）
- [ ] React useEffect 中有 cleanup 函数（清除 timer / 取消订阅 / 断开 WebSocket）
- [ ] 无闭包持有大对象引用导致内存泄漏（如 `useEffect(() => { const big = huge; }, [])` 未清理）
- [ ] 无 EventEmitter 未移除监听器（`addEventListener` 对应 `removeEventListener`）
- [ ] 线程池/连接池大小有上限（不会无限创建导致 OOM）

#### 2.9 并发与异步安全
- [ ] 无共享可变状态未加锁（多线程/多协程写同一变量）
- [ ] 前端状态更新考虑并发（`setState(prev => ...)` 而非 `setState(state + 1)`）
- [ ] `Promise.all` vs 顺序 await 选择正确（独立请求用 `all`，有依赖的用顺序）
- [ ] 无 floating promise（未 await 也未 catch 的 Promise）
- [ ] 无 `async` 函数内同步抛出异常（应 reject 而非 throw 在 Promise 外）
- [ ] 多步操作有事务或补偿逻辑（要么全成功，要么全回滚）

#### 2.10 依赖与兼容性
- [ ] 无循环依赖（模块 A → B → A）
- [ ] 新增/删除依赖的版本在 `package.json`/`pom.xml` 中正确声明
- [ ] 未引入不必要的传递依赖（只导入用到的包/模块）
- [ ] API 变更是否向后兼容？（新增字段可选，不删字段，不改变字段类型）
- [ ] DB 迁移有回滚方案（Flyway 迁移可逆？数据回填脚本已准备？）

#### 2.11 日志与可观测性
- [ ] 关键操作有日志（登录、支付、删除、权限变更）
- [ ] 日志级别正确（ERROR=需要人工处理，WARN=可自动恢复，INFO=关键里程碑，DEBUG=诊断信息）
- [ ] 日志中无敏感信息（密码/Token/身份证号/手机号已脱敏或移除）
- [ ] 异常日志含完整堆栈和上下文（不是 `log.error(e.getMessage())` 而是 `log.error("操作失败 userId={}", id, e)`）
- [ ] 无高频路径打 INFO 日志（热路径仅 DEBUG 级别，避免日志爆炸）

#### 2.12 文档（非显而易见的部分）
- [ ] 所有 `// HACK` / `// FIXME` / `// TODO` 有对应的 issue 编号或明确原因
- [ ] 非显而易见的业务规则有注释 WHY（不是 WHAT——代码已说清做了什么）
- [ ] 公开 API / 导出函数有 JSDoc / JavaDoc（参数含义 + 返回值 + 可能异常）
- [ ] 废弃方法有 `@deprecated` 标注并指向替代方案
- [ ] 有副作用的操作在名称或注释中标明（"更新缓存"、"发送事件"）

#### 2.13 测试质量
- [ ] 新增测试覆盖率 ≥80%
- [ ] 每个测试只测一个行为（it 名不含"和"/"以及"）
- [ ] 测试名描述行为而非实现（"返回 401"而非"调用 validateToken 一次"）
- [ ] 有正常路径 + 边界条件 + 异常路径的测试
- [ ] 测试之间无共享可变状态（每个测试独立）
- [ ] 无 flaky 测试（无 `setTimeout`/`sleep` 等时间依赖）

### 阶段 3 — 最终自检（硬性闸门）

**在调用 `os-ship` 前，必须逐项执行并确认通过：**

```
[REVIEW] Spec 合规: ✓/✗
[REVIEW] 死代码与冗余: ✓/✗
[REVIEW] 重复代码: ✓/✗
[REVIEW] 命名可读性: ✓/✗
[REVIEW] Code Smells: ✓/✗
[REVIEW] 错误处理: ✓/✗
[REVIEW] 安全: ✓/✗
[REVIEW] 性能: ✓/✗
[REVIEW] 资源管理: ✓/✗
[REVIEW] 并发与异步安全: ✓/✗
[REVIEW] 依赖与兼容性: ✓/✗
[REVIEW] 日志与可观测性: ✓/✗
[REVIEW] 文档: ✓/✗
[REVIEW] 测试质量: ✓/✗
[REVIEW] 全量测试: <N passed, 0 failed>
[REVIEW] Lint: ✓/✗
[REVIEW] 类型检查: ✓/✗
```

- 任一 ✗ → 回到对应 task 修复，不得跳过
- Lint/类型检查/全量测试 不通过 → 绝对不得调用 `os-ship`
- 全部 ✓ → 输出 `[REVIEW] 审查通过，可归档`

### 审查反馈处理协议
- Critical 问题 → 立即修复后再继续
- Important 问题 → 继续前修复
- Minor 问题 → 可稍后处理
- 审查者有误 → 用技术推理反驳（附代码/测试证据），禁止防御性争论
- 禁止：盲目同意审查意见、不验证就实施、批量修改后不测试、表演性附和

## 其他规则

- **跨会话暂停/恢复：** 实施中断前确保 tasks.md 完成状态是最新的。下次会话开始时读取 tasks.md 找到第一个 `[ ]` 项继续。
- **实施中发现 design 也得改：** Spec 没变但技术方案走不通 → 先更新 design.md 并告知用户原因，再继续。

## 完成后

Code Review 通过 → 调用 `os-ship` 归档。

### Spec 冲突处理

**模型（正在实施中）：**
```
[WORKFLOW] 判定表情况: Spec 与测试冲突 → Spec 优先原则 → 暂停与用户决策
[WORKFLOW] 当前阶段: Implement (RED — Spec 冲突)
[WORKFLOW] 前置条件: RED 测试编写中发现 Spec 与现有 HttpError 枚举不一致

### 3.1 RED 测试编写中发现 Spec 冲突

Spec 要求"过期 token 返回 410 Gone"，
但当前 HttpError 枚举只有 400、401、403、404、500，无 410。

按 Spec 优先原则，有两个选项：
A. 在 HttpError 枚举中新增 410 — 语义正确，但增加新状态码
B. 改用 401 — 语义接近（认证/授权失败），不增加新状态码

建议选 A，因为 410 语义明确（"资源已过期"），且后续其他过期场景可复用。
你怎么看？
```
