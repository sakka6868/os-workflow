# os-trace：系统化调试 + 数据流溯源

## 何时调用

任何技术问题——测试失败、生产 Bug、异常行为、性能问题、构建失败、集成问题。特别必须在以下情况走完整流程：
- 时间紧迫想"快速修一下"
- 看起来"很明显"是什么问题
- 之前已尝试过多个修复但未成功
- 你不完全理解这个问题

**铁律：禁止在找到根因之前提出任何修复方案。** 症状修复 = 失败。

---

## 阶段 1：根因调查

**1.1 仔细读错误信息：** 不要跳过任何错误或警告。堆栈跟踪往往包含精确的解决方案。注意行号、文件路径、错误码。

**1.2 稳定复现：** 能可靠触发吗？精确步骤是什么？每次都发生吗？若不能复现 → 收集更多数据，不要猜测。

**1.3 检查近期变更：** `git diff`、最近提交、新增依赖、配置变更、环境差异。

**1.4 多组件系统取证：** 在每层组件边界添加诊断埋点——记录进入/离开数据、验证环境/配置传播、检查每层状态。运行一次收集证据，定位断点位置，然后聚焦调查该组件。

**1.5 数据流溯源：** 对深层调用栈中的错误，反向追踪：坏值从哪里来？谁传入了坏值？持续向上追踪直到找到源头。**在源头修复，不在症状处修复。**

```
前端：组件 → hook → API 调用 → 网络请求 URL → 网关路由 → 后端 Controller
后端：Controller → Service → Repository → 数据表/外部服务/gRPC
```

数据流核心检查项：

| 场景 | 检查 |
|------|------|
| 角标有数字但列表为空（前端） | 角标的数据源 API 和列表的数据源 API 是否相同？ |
| 实时刷新不生效 | SSE 事件名是否匹配？后端 event publisher 在业务流程中是否被实际调用？ |
| 字段为空/null | 前端 DTO 字段名是否匹配后端返回？后端 Service 是否填充了该字段？ |
| 写入成功但读不出来 | 写和读是否走同一张表/同一个查询条件？ |

---

## 阶段 2：模式分析

**2.1 找可工作的同类代码：** 在同一个代码库中，什么类似功能是正常工作的？

**2.2 对比参考实现：** 完整阅读参考实现——不要略读，读每一行。

**2.3 列出差异：** 逐条列出工作代码与损坏代码之间的所有差异，永远不要假设"这不可能是原因"。

**2.4 理解依赖：** 这个功能依赖什么其他组件、设置、配置、环境？

---

## 阶段 3：假设与验证

**3.1 形成单一假设：** 明确陈述"我认为 X 是根因，因为 Y"。写下来。具体的，不模糊的。

**3.2 最小化验证：** 用尽可能小的改动来验证假设。一次只改一个变量。

**3.3 验证后再继续：** 成功了？→ 进入阶段 4。没成功？→ 形成新假设。不要在原假设上叠加更多修复。

**3.4 不知道就说不知道：** 说"我不理解 X"。不要假装知道。

---

## 阶段 4：实施修复

**4.1 先写失败测试：** 最简单的复现用例——自动化优先，没有测试框架就用一次性脚本。修复前必须存在。

**4.2 实施单一修复：** 只解决已确认的根因。一次改一处。禁止"顺路改一下"。禁止捆绑重构。

**4.3 验证修复：** 测试通过了吗？其他测试没有被破坏？问题确实解决了？

**4.4 修复不生效时的 3 次上限规则：**
- **少于 3 次：** 带着新信息回到阶段 1 重新分析
- **3 次及以上：** **立即停止**，不要再试第 4 次。质疑架构：模式本身是否有问题？是否"靠惯性硬撑"？每次修复是否暴露了新的共享状态/耦合问题？→ 与用户讨论后再继续

---

## 危险信号（立即回到阶段 1）

如果你发现自己在想以下任何一句，**停止并回到阶段 1**：
- "先快速修一下，后面再调查"
- "试试改 X 看看效果"
- 一次性改多处然后跑测试
- "不用写测试，手动验证就行"
- "应该是 X，修一下试试"
- "不完全理解但这个可能管用"
- 2 次失败后还想"再试一次"
- 每次修复在另一个地方暴露了新问题
- 用户说"停一下猜的""搞清楚再说"→ 立即回到阶段 1

**完成标准：** 找到数据流中的断点位置，明确告知用户"根因是 X 层的 Y 调用与实际数据源 Z 不一致"，**然后**再写 spec。

## 完成后

根因定位完成 → 调用 `os-spec` 编写 Delta spec → 调用 `os-design` 生成 tasks.md → 调用 `os-build` 进入 TDD 修复。
